SUBMISSION TYPE: Software

NAME: Improper Enforcement of Identifier Uniqueness

DESCRIPTION:

The product generates, assigns, or accepts an identifier that is expected
to be unique, but does not enforce its uniqueness atomically when storing
it, allowing multiple entities to end up sharing the same identifier.

---

This weakness typically occurs when developers rely on the low likelihood
of a collision (e.g., short random strings or sequential numbers) rather
than on a database-level guarantee, or when they implement a flawed logic
flow that lacks atomic verification and retry mechanisms. Instead of
verifying existence and handling conflicts through database-level
constraints or retry loops, the product assigns or accepts an identifier
that is already in use.

The weakness can appear in several forms. The product may generate an
identifier and insert it without handling a unique constraint violation. It
may check whether an identifier exists and then store it in a separate,
non-atomic step, leaving a window in which concurrent requests can claim
the same value. It may also accept an identifier supplied by the client
without verifying that it is not already allocated.

Depending on how the collision is handled, it may result in an existing
resource being overwritten, in one user gaining access to another user's
data, or in the takeover of an existing resource such as a short-lived
token, access code, or profile link.
