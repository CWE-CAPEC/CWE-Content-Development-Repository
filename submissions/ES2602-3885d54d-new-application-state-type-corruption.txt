NAME: Application State Type Corruption (ASTC) - Persistent Data Type Assumptions in PHP Applications

DESCRIPTION:

This weakness occurs when an application assumes that persisted data
structures will always conform to an expected type (e.g., objects) without
validating the retrieved state. In some cases, the application itself may
unintentionally mutate or convert the stored data into a different type
(e.g., arrays instead of objects) during normal processing. Subsequent code
that accesses properties or methods assumes the original type, leading to
persistent fatal errors across multiple modules. This can result in
authentication failures, system crashes, or other systemic failures.
Variations include any situation where unsafe assumptions about type
integrity are made across execution paths and persistent state mutation is
possible.

Generalizability

This pattern is not language-specific. Although initially observed in PHP,
similar behavior has been confirmed across:
- Multiple languages (including Java). For example, in Axway SecureTransport,
the issue did not stem from the language itself (as it doesn't allow changing
data types), but from application-level handling (e.g., encoding/decoding
inconsistencies), where input was not transformed as expected and was instead
treated as a different data type, leading to the same class of failure
- Different frameworks and technology stacks
- Both web applications and enterprise softwares

The root cause is architectural, not related to dynamic typing. The corruption
originates from:
- Internal processing inconsistencies
- Encoding/decoding mismatches (e.g., authentication flows)
- Storage/retrieval transformations
- Application logic mutating persisted state (a key distinguishing
characteristic of this weakness)

Cross-Product Presence

This pattern has been identified across multiple real-world products, indicating
it is:
- Systematic and repeatable
- Present in shared design patterns
- Likely widespread across additional codebases

Impact Scope

This issue is often misclassified as DoS. However, it more accurately represents
persistent application state corruption or critical functionality disruption
(e.g., complete authentication failure where no users can log in)

Depending on context and execution flow, impacts include:
- Authentication and security control bypass (MFA, lockout, rate limiting). In
one observed case, malformed input led to authentication bypass and privilege
escalation due to corrupted state propagation
- Persistent state desynchronization
- Cross-module failure propagation
- Application-wide instability or collapse
- Potential account takeover scenarios

(Additional impact scenarios are detailed in the submitted research paper in the
mega link)

Key Distinction

The defining property is:

"The application mutates and persists structurally invalid state, and later
execution paths assume integrity without validation"

This combination of self-mutation + persistence + cross-module assumptions is
not covered by existing CWE entries


MODES OF INTRODUCTION:

Phase: Architecture and Design

Note: The weakness can be introduced when the application's design
does not define or enforce structural/type invariants at persistence
boundaries — i.e., no contract is established for what a "valid"
persisted state looks like before it is written or before it is
rehydrated.


Phase: Implementation

Note: Even where a valid structure is intended, this weakness is
introduced when application logic (serialization, ORM mapping,
encoding/decoding, or normalization routines) transforms data into a
structurally inconsistent form before persisting it, and no validation
step is added at write-time or read-time to catch the inconsistency.

COMMON CONSEQUENCES:

Scope: Availability

Impact: DoS: Crash, Exit, or Restart; DoS: Instability

Likelihood: High

Note: Persisted state corruption can propagate across requests,
leading to persistent authentication failure or functional
unavailability affecting some or all users, not just the original
triggering request. In some observed cases, the corrupted state
disrupted application access entirely, rendering core functionality
unusable until the underlying persisted state was manually
corrected. The specific manifestation is highly dependent on
application context — how a given codebase handles the resulting
inconsistent state determines whether the outcome is a contained
error, a degraded feature, or a full outage.


Scope: Authentication; Access Control

Impact: Bypass Protection Mechanism; Gain Privileges or Assume Identity

Likelihood: Medium

Note: When corrupted state desynchronizes authentication or
authorization logic, downstream modules may make incorrect trust
decisions based on the invalid structure, potentially enabling bypass
or privilege escalation. In one observed case, corrupted state led to
an account-takeover-like condition where the application granted an
authenticated-looking session (dashboard access with a functioning
logout control) without any underlying valid account. Because the
outcome depends on how each application's logic interprets the
malformed state, the same root cause can also result in the opposite
behavior — an application may instead treat the anomalous state as
intrusive and lock out a legitimate account. This variability across
implementations is itself notable: the same weakness can manifest as
either an authentication bypass or a false-positive lockout, depending
entirely on how downstream logic reacts to structurally invalid
persisted state.


Scope: Integrity

Impact: Unexpected State; Alter Execution Logic

Likelihood: Medium

Note: Once invalid state is persisted and treated as canonical, any
module that consumes it inherits the inconsistency, causing cascading
failures across otherwise-unrelated components. Because the range of
possible downstream behaviors is broad and context-dependent, this
weakness functions less like a single well-defined bug and more like a
precursor condition — an attack vector that can give rise to many
distinct classes of impact (authentication bypass, lockout, crash,
privilege escalation) depending on how a specific application is
built.

INTRO TEXT:

The following example is drawn from CI4MS, an open-source CodeIgniter
4 CMS. The application's login lockout logic retrieves a "locked"
record from the database and assumes it will always be an object,
without validating its structure before accessing a property on
it. This example demonstrates a persistent Availability impact
(authentication denial-of-service).

BAD CODE:
LANGUAGE: PHP

```php
$where = ['islocked' => true];
$where_or = ['username' => $username, 'ip_address' => $this->ipAddress];
$countLocked = $this->userModel->getOneOr('locked', $where, 'id DESC', 'id,counter,expiry_date', $where_or);

if (!$countLocked) $countLockedValue = 0;
else $countLockedValue = $countLocked->counter;
```

EXPLANATORY TEXT:

`getOneOr()` is expected to return either an object representing a
single "locked" record, or a falsy value if no record exists. The code
only guards against the falsy case (`if (!$countLocked)`); it does not
verify that a truthy return value is actually an object before
accessing `$countLocked->counter`.

Under certain internal conditions, the persisted "locked" record can
be retrieved in an array-structured form rather than the expected
object form — the application itself produces this inconsistency
during normal processing, not the attacker directly. Once such a
record exists, every subsequent login attempt that reaches this code
path retrieves it and immediately fails, since PHP raises a fatal
error when a property is accessed on an array (`Attempt to read
property "counter" on array`).

Impact: Because this check runs before authentication is evaluated,
the resulting fatal error blocks login for the affected account on
every subsequent attempt — including for legitimate users and
administrators — until the underlying database record is manually
corrected. This is a persistent Availability impact: a single instance
of corrupted state causes an ongoing denial-of-service condition that
outlives the original triggering request.

GOOD CODE:
LANGUAGE: PHP

```php
$where = ['islocked' => true];
$where_or = ['username' => $username, 'ip_address' => $this->ipAddress];
$countLocked = $this->userModel->getOneOr('locked', $where, 'id DESC', 'id,counter,expiry_date', $where_or);

if (!$countLocked || !is_object($countLocked) || !property_exists($countLocked, 'counter')) {
    $countLockedValue = 0;
} else {
    $countLockedValue = $countLocked->counter;
}
```

The corrected version validates both that the retrieved record is an
object and that it has the expected `counter` property before
accessing it, falling back to a safe default otherwise. This prevents
a single malformed record from causing a persistent authentication
outage, and creates an opportunity to log or alert on the unexpected
structure for further investigation.

INTRO TEXT:

The following example shows the same weakness occurring outside of
authentication logic entirely — in a settings/preferences flow — to
illustrate that this weakness is not limited to login or lockout
mechanisms. This example demonstrates an Availability impact confined
to a single feature rather than the whole application.

BAD CODE:
LANGUAGE: PHP

```php
class UserPreferences {
    public $theme = 'dark';
}

// Module A: a settings update endpoint
function update_preferences($input) {
    // $input may come directly from $_POST['prefs'] as an associative
    // array instead of the expected UserPreferences structure.
    // No validation is performed before persisting it.
    $_SESSION['user_prefs'] = $input;
}

update_preferences(['theme' => 'light']);

// Module B: the dashboard, rendered in a separate request
$prefs = $_SESSION['user_prefs'];
echo "Current theme: " . $prefs->theme;
// Fatal error: Attempt to read property 'theme' on array
```

EXPLANATORY TEXT:

The settings endpoint persists whatever shape it receives without
checking it against the `UserPreferences` contract. The dashboard,
running in a completely separate request, assumes the session still
holds a `UserPreferences` object. Because the corrupted value is
stored in the session rather than a one-off variable, it persists
across every subsequent page load until the session is cleared or
overwritten.

Impact: This produces a per-user Availability impact — the affected
user's dashboard becomes permanently broken on every subsequent visit,
without any error occurring in the module (settings update) where the
actual corruption was introduced. This illustrates how the weakness's
blast radius depends entirely on which downstream module happens to
consume the corrupted state, not on where it originated.

GOOD CODE:
LANGUAGE: PHP

```php
function render_dashboard_safe() {
    $prefs = $_SESSION['user_prefs'] ?? null;

    if (!($prefs instanceof UserPreferences)) {
        $theme = is_array($prefs) && isset($prefs['theme']) ? $prefs['theme'] : 'dark';
        $prefs = new UserPreferences();
        $prefs->theme = $theme;
    }

    echo "Current theme: " . $prefs->theme;
}
```

INTRO TEXT:

The following example illustrates a non-crashing manifestation of the
same weakness in Python, where corrupted persisted state causes an
incorrect authorization decision rather than a fatal error. This
example demonstrates an Access Control impact.

BAD CODE:
LANGUAGE: Python

```python
class UserSession:
    def __init__(self, user_id, role="user"):
        self.user_id = user_id
        self.role = role

# Module A: a profile-update endpoint
def update_session_state(store, session_id, input_data):
    # input_data is a raw dict decoded from a request body,
    # e.g. {"user_id": 42, "role": "user"}, rather than a UserSession
    # instance. No validation is performed before persisting it.
    store[session_id] = input_data

update_session_state(store, "sess_123", {"user_id": 42, "role": "user"})

# Module B: an admin panel access check, evaluated in a later request
def check_admin_access(store, session_id):
    session = store[session_id]
    # Assumes session is a UserSession instance with attribute access;
    # a dict does not raise here because .get behaves permissively
    # if this code were written defensively -- but if written as
    # session.role, it would instead silently evaluate a stale or
    # default attribute depending on how the surrounding code
    # tolerates the mismatch, rather than crashing outright.
    if getattr(session, "role", "admin") == "admin":
        grant_admin_access(session.user_id)
```

EXPLANATORY TEXT:

Here, `getattr(session, "role", "admin")` is written with a default
fallback value intended for a different purpose (avoiding a crash on
missing attributes), but because `session` is actually a plain `dict`
rather than a `UserSession` object, `getattr` cannot find a `role`
attribute on it at all and silently returns the fallback default —
`"admin"` — regardless of the role that was actually persisted.

Impact: This results in a silent Access Control impact — a user
session that was persisted with `role: "user"` is granted admin
access, not because of any explicit privilege escalation exploit, but
because the code's fallback-on-missing-attribute behavior interacts
with the structurally-wrong persisted type in a way that defeats the
intended authorization check. No error or crash occurs, which makes
this manifestation harder to detect than the DoS-style examples above.

GOOD CODE:
LANGUAGE: Python

```python
def check_admin_access_safe(store, session_id):
    session = store.get(session_id)
    if not isinstance(session, UserSession):
        raise ValueError("Invalid or corrupted session state")
    if session.role == "admin":
        grant_admin_access(session.user_id)
```

INTRO TEXT:

The following example shows the weakness in a statically-typed
language, where a loosely-typed container is used to bridge dynamic
data (such as decoded JSON) into the rest of the application,
bypassing compile-time type guarantees. This example demonstrates an
Availability impact via an unrecovered runtime panic.

BAD CODE:
LANGUAGE: Go

```go
type UserPreferences struct {
    Theme string
}

var session = map[string]interface{}{}

// Module A: an update handler
func updatePreferences(input interface{}) {
    // input may be a map[string]interface{} decoded from a JSON
    // request body, not a UserPreferences struct. No validation
    // is performed before persisting it.
    session["user_prefs"] = input
}

func main() {
    updatePreferences(map[string]interface{}{"theme": "light"})

    // Module B: a separate render function, called later
    prefs := session["user_prefs"].(UserPreferences) // type assertion
    fmt.Println("Current theme:", prefs.Theme)
    // panic: interface conversion: interface {} is map[string]interface {},
    // not main.UserPreferences
}
```

EXPLANATORY TEXT:

Storing data as `interface{}` allows any type to be persisted without
a compile-time guarantee that it matches the expected struct. The
single-value type assertion `.(UserPreferences)` assumes the stored
value's type without checking it, so Go's runtime panics the moment
the assumption is false.

Impact: An unrecovered panic in Go terminates the goroutine handling
the request, and if unhandled by surrounding middleware, can crash the
entire process — an Availability impact that, depending on deployment
(e.g., no per-request recovery middleware), can affect all concurrent
users of the service, not just the one whose data was malformed.

GOOD CODE:
LANGUAGE: Go

```go
prefs, ok := session["user_prefs"].(UserPreferences)
if !ok {
    // Value is not the expected type; fall back to a safe default
    prefs = UserPreferences{Theme: "dark"}
}
fmt.Println("Current theme:", prefs.Theme)
```

INTRO TEXT:

The following example shows a silent Authentication impact in
JavaScript, where corrupted persisted state results in a user being
treated as authenticated without a valid underlying account. This
example demonstrates an Authentication bypass impact, distinct from
the crash-based examples above.

BAD CODE:
LANGUAGE: JavaScript

```javascript
class AuthenticatedSession {
  constructor(userId) {
    this.userId = userId;
    this.isAuthenticated = true;
  }
}

// Module A: a token-refresh endpoint
function persistSession(store, sessionId, input) {
  // input is expected to be an AuthenticatedSession instance, but
  // if constructed from a partially-processed token payload
  // (e.g. JSON.parse of a refresh token body), it may instead be
  // a plain object that happens to have compatible-looking fields.
  store[sessionId] = input;
}

persistSession(store, "sess_abc", { userId: undefined, isAuthenticated: true });

// Module B: the dashboard route, evaluated on a later request
function renderDashboard(store, sessionId) {
  const session = store[sessionId];
  if (session.isAuthenticated) {
    // No check that session is actually an AuthenticatedSession
    // instance, or that userId corresponds to a real account.
    showDashboard(session.userId);
  }
}
```

EXPLANATORY TEXT:

The persisted object satisfies the surface-level shape the dashboard
route checks for (`isAuthenticated: true`) without ever having gone
through the actual authentication flow that constructs a real
`AuthenticatedSession` tied to a verified account. Because JavaScript
does not enforce that `session` is truly an instance of
`AuthenticatedSession`, and the code only checks a single boolean
property rather than the object's type or the validity of `userId`,
the dashboard renders as if the user is logged in.

Impact: This results in an Authentication impact — a session that was
never validated against a real account is treated as authenticated,
granting the appearance of a logged-in state (e.g., a dashboard with a
functioning logout control) without any underlying valid account. This
is a more severe manifestation than a crash, since the application
continues running and actively grants access rather than failing
safely.

GOOD CODE:
LANGUAGE: JavaScript

```javascript
function renderDashboardSafe(store, sessionId) {
  const session = store[sessionId];
  if (!(session instanceof AuthenticatedSession) || !session.userId) {
    return redirectToLogin();
  }
  showDashboard(session.userId);
}
```

INTRO TEXT:

The following example shows the weakness in C, where the absence of a
type tag or structure validation on a persisted buffer allows adjacent
memory to be silently reinterpreted as a different, more privileged
structure. This example demonstrates a silent Access Control /
privilege escalation impact with no crash at all.

BAD CODE:
LANGUAGE: C

```c
typedef enum { TYPE_USER_PREFS, TYPE_ADMIN_PREFS } PrefsType;

typedef struct {
    PrefsType type;
    char theme[32];
} UserPreferences;

typedef struct {
    PrefsType type;
    char theme[32];
    int  admin_level;
} AdminPreferences;

static unsigned char session_store[128];

// Module A: writes a UserPreferences-sized buffer without
// validating that its size matches its claimed type
void update_preferences(void *input, size_t input_size) {
    memcpy(session_store, input, input_size);
}

void handle_settings_update(void) {
    UserPreferences fake = { TYPE_USER_PREFS, "light" };
    update_preferences(&fake, sizeof(fake));
}

// Module B: reads the buffer later, assuming it is always safe
// to reinterpret as the larger AdminPreferences structure
void render_dashboard(void) {
    AdminPreferences *prefs = (AdminPreferences *)session_store;
    printf("Theme: %s\n", prefs->theme);
    printf("Admin level: %d\n", prefs->admin_level);
}
```

EXPLANATORY TEXT:

`update_preferences()` writes only `sizeof(UserPreferences)` bytes
into `session_store`, but `render_dashboard()` reinterprets the same
buffer as the larger `AdminPreferences` structure without checking the
`type` tag or verifying that enough bytes were actually written for
that structure. The `admin_level` field read by `render_dashboard()`
falls outside the bytes that were actually written, so it reads
whatever bytes happen to already be present in that memory
(uninitialized memory, or leftover data from a previous unrelated
write).

Impact: This produces a silent Access Control impact with no crash and
no visible error: depending on what happens to occupy that memory, a
normal user's session can be read back as having an arbitrary
`admin_level`, potentially granting elevated privileges the user was
never assigned. Because nothing fails or logs an error, this
manifestation is the hardest of all the examples here to detect
through normal application monitoring.

GOOD CODE:
LANGUAGE: C

```c
void update_preferences_safe(void *input, size_t input_size, PrefsType claimed_type) {
    size_t expected_size = (claimed_type == TYPE_ADMIN_PREFS)
        ? sizeof(AdminPreferences)
        : sizeof(UserPreferences);

    if (input_size != expected_size) {
        // Reject writes that don't match the claimed type's actual size
        return;
    }
    memcpy(session_store, input, input_size);
}

void render_dashboard_safe(void) {
    PrefsType *type_tag = (PrefsType *)session_store;
    if (*type_tag != TYPE_ADMIN_PREFS) {
        printf("Admin level: 0 (not an admin session)\n");
        return;
    }
    AdminPreferences *prefs = (AdminPreferences *)session_store;
    printf("Theme: %s\n", prefs->theme);
    printf("Admin level: %d\n", prefs->admin_level);
}
```

The corrected version validates the size of the data before persisting
it, ensuring that the stored buffer is consistent with the claimed
structure type. When the data is later consumed, it verifies the
embedded type tag before reinterpreting the buffer as an
AdminPreferences structure. Together, these checks prevent a smaller
or differently structured object from being treated as a more
privileged structure, eliminating the possibility of reading
unintended memory as an admin_level and preventing the resulting
Access Control impact.

DETECTION METHODS:

Method: Automated Static Analysis

Desc: LLM-assisted code review, given a dataset of known vulnerable
code patterns (persisted data read and used without a preceding
type/shape check), can search a codebase for structurally similar
patterns regardless of variable names or exact logic shape. This bug
is an application logic flaw in how the app does things, and requires
knowing the necessary locations, inputs, and comparing behavior end to
end — so an LLM can search for this pattern across source code in any
shape, given a dataset of vulnerable code examples to reference.

Effectiveness: Moderate

Notes: This weakness is an application-logic flaw rather than a fixed
syntactic pattern — it depends on tracing how a specific value flows
from a persistence write to a later persistence read, across different
variable names, functions, and modules. Traditional automated static
analyzers struggle with this, since the issue isn't a bad function
call but a missing validation step relative to a data flow the tool
has to understand contextually. LLM-assisted review is meaningfully
more capable of this kind of contextual pattern matching than
conventional static analyzers, making it one of the more efficient
available methods for this weakness class. However, it comes with a
con: AI could hallucinate or miss context/logic of the app and flag
incorrect findings, so manual verification is required. Regarding full
automation (tracing the whole process end-to-end automatically), this
would be very exhaustive and may not lead to desired results, since
variables, logic, and input context differ heavily app to app —
someone may eventually develop better automated testing styles for
this, but it remains inherently difficult to fully automate given how
logic-dependent this weakness is. This method also extends to compiled
binaries (.exe): reverse engineering to recover source or just
depending on source code, then scanning the recovered code via AI or
manual review follows the same approach described above.

----

Method: Manual Static Analysis - Source Code

Desc: Manually reviewing source code to identify locations where data
is retrieved from persistent storage (database, session, cache) and
used without a type or structure check (e.g., missing instanceof,
is_object, property_exists, or schema validation).

Effectiveness: Moderate, but somewhat exhaustive

Notes: More reliable than automated static analysis for this weakness
since a human reviewer can trace logic and context accurately, but it
is time-intensive, since instances can appear anywhere persisted state
is read — similar in scope to auditing an entire codebase for missing
output encoding in an XSS review. This can be tolerated as a method,
but requires checking many areas across the codebase.


Method: Automated Dynamic Analysis

Desc: Automated tooling can probe live applications by submitting
known trigger patterns (malformed/mixed-type input) to common entry
points, particularly authentication flows, and observing whether the
application later fails, behaves inconsistently, or produces evidence
of corrupted persisted state. In my own testing, this focused mostly
on the authentication component, and automation could work by scanning
domains, getting into login pages, and trying out common/known
techniques for triggering this weakness using specific payloads,
instead of manually trying each domain individually. For real-world
web apps, this can also involve getting into frontend sources (JS
files) and having an AI scan them, or scanning them manually — though
this is generally harder than working with backend source code
directly.

Effectiveness: Moderate

Notes: Effective for the specific classes of entry points already
known to be common triggers (e.g., login/session handling), but
coverage is limited to what the tooling is configured to target — the
weakness can occur anywhere persisted state is written and reused, not
only in authentication logic, so blind automated scanning risks
missing instances outside the tested surface.

Method: Manual Dynamic Analysis / Black Box Testing (including fuzzing)

Desc: Since the bug is context-dependent, this requires testing a
variety of payloads, as some will work against some targets/fields and
not others. For example: supplying a dict/array where an object is
expected may trigger the weakness, but supplying a dict where a dict
is already expected won't; a value like '@gmail.com may trigger it if
the field is later base64-encoded, but not if it's treated as a plain
string. Based on the app's context, logic, and how it's built, you
keep iterating a set of payloads to assess how the process behaves and
identify which kinds of payloads work for that specific edge case.

trigger every instance of this weakness, since each manifestation can

The effectiveness of this payload depends on context, such as input

Notes: This was the primary method used during initial research,

Method: Architecture or Design Review

Desc: When you review an application's architecture and design, you
start to understand how the app works — what locations exist, what
data is written, what data types are used, and what persistent storage
mechanisms are involved — which gives insight into how this weakness
could be generated. If you find one instance, this understanding can
help you identify the same shared pattern repeated across multiple
components/processes.

Effectiveness: High

Notes: Since the weakness is a property of the design (absence of a
validation contract at persistence boundaries) rather than something
only observable through a specific triggering input, this method can
surface the vulnerable pattern even in code paths not yet exercised by

focused heavily on the authentication component, but design review of
the broader application revealed the same unvalidated-access pattern
could also occur outside authentication entirely — for example, in
dashboard/preference rendering logic reading persisted state that was
never validated at write time. Once one instance is found in a
codebase, this method is useful for identifying whether the same
pattern repeats elsewhere, since a missing validation contract is
often applied inconsistently rather than uniformly across the
codebase.

POTENTIAL MITIGATIONS:

Phase: Architecture and Design

Description: Define and enforce an explicit structural/type contract
at every persistence boundary — i.e., specify what a "valid" persisted
record looks like before it is ever written or read, rather than
relying on an implicit assumption that data will always arrive in its
expected shape.

Effectiveness: High

Effectiveness Notes: This is the most effective mitigation because it
addresses the weakness at its root: the absence of a defined contract
is what allows a structurally-invalid value to be silently accepted,
both at write time and at read time. Establishing this contract during
design also makes the remaining implementation-level mitigations
(below) straightforward to apply consistently.


Phase: Implementation

Description: Validate the structure and type of any value retrieved
from persistent storage (database, session, cache, or similar) before
it is used, rather than assuming it matches the type it was originally
written as. In weakly-typed or dynamically-typed languages, this means
explicit checks such as `is_object()`/`instanceof` (PHP),
`isinstance()` (Python), type assertions with the "comma ok" idiom
(Go), or `instanceof` (JavaScript) before accessing properties or
methods on the retrieved value.

Effectiveness: High

Effectiveness Notes: This directly prevents the weakness from causing
a fatal error, silent misbehavior, or incorrect trust decision,
regardless of how the persisted value became structurally invalid in
the first place. It is effective even when the root cause of the
corruption (e.g., an upstream encoding mismatch or incorrect cast) is
never identified or fixed, since it treats every read from persistent
storage as untrusted until validated.


Phase: Implementation

Description: Validate and normalize data before it is persisted, not
only when it is read back. This includes enforcing input validation at
entry points (addressing CWE-20-style precursors) and ensuring that
any transformation applied to the data (serialization, ORM mapping,
encoding/decoding) produces output that conforms to the expected
structure before it is written to storage.

Effectiveness: Moderate

Effectiveness Notes: Validating on write reduces how often invalid
state is introduced in the first place, but on its own it is not
sufficient: it does not protect against cases where the application's
own internal processing corrupts otherwise-valid data after the
initial write (as documented in the CI4MS case, where no malformed
external input was involved). This mitigation is most effective when
combined with validation on read, rather than used as a substitute for
it.


Phase: Implementation

Description: In languages or systems where a persisted value's actual
type must be reconstructed dynamically (e.g., binary/serialized
formats, or loosely-typed containers such as `interface{}` in Go or
`void*`/untyped buffers in C), include an explicit type tag or schema
identifier alongside the data itself, and verify that tag before
reinterpreting the underlying bytes or structure.

Effectiveness: Moderate

Effectiveness Notes: This is particularly important for preventing the
more severe, silent manifestations of this weakness (such as the C
example where a smaller struct is misread as a larger, more privileged
one), since without an explicit tag there is no reliable way to detect
a structural mismatch before the data is used.


Phase: Testing

Description: Include structural/type mismatch scenarios in test suites
for any code path that reads from persistent storage — for example,
deliberately persisting a value in an unexpected shape and asserting
that the consuming code fails safely (e.g., returns a default or
raises a handled error) rather than crashing unhandled or silently
proceeding with incorrect assumptions.

Effectiveness: Moderate

Effectiveness Notes: Testing can catch regressions once the
mitigations above are in place, but is unlikely to discover the
weakness on its own in the first place, since the conditions that
produce structurally-invalid persisted state are often
context-dependent and not obvious from reading a single function in
isolation. This mitigation is best used to confirm that
Architecture/Design and Implementation-phase fixes are actually
effective, not as a primary detection method.


Phase: Operation

Description: Where feasible, monitor and alert on unexpected
structural mismatches encountered when reading persisted state (e.g.,
logging when a validation-on-read check fails), so that ongoing
corruption can be detected and investigated even if the underlying
root cause has not yet been fully diagnosed or fixed.

Effectiveness: Defense in Depth

Effectiveness Notes: This does not prevent the weakness, but reduces
the risk of it going unnoticed — particularly important for the
silent, non-crashing manifestations of this weakness (such as
incorrect authorization decisions), which would otherwise produce no
visible symptom at all.
