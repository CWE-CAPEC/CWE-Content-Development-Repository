SUBMISSION TYPE: Hardware

NAME: Improper Request Propagation before Data Reception in Write Transactions in a Bus Architecture

SUMMARY:

The product uses a multi-manager shared bus architecture with an
on-chip interconnect that speculatively propagates a request for a
write transaction, but it does not ensure that the remaining steps -
required by the manager module to complete the request - are fulfilled
in a timely manner.

TECHNICAL NUANCE:

Here, the word "speculatively" refers to the fact that the
interconnect propagates the request assuming that the manager will at
some point provide the data, thus releasing the use of the bus.

[NO EXTENDED DESCRIPTION - PREVIOUS PORTIONS WERE MOVED TO background
details, modes of introduction, and common consequences.]

BACKGROUND DETAILS:

Some products may use an architecture with a shared bus that is
accessible by multiple devices, in which these devices can issue
requests that utilize the shared bus. There may be an on-chip
interconnect based on a protocol that manages the devices' requests to
the bus and enforces the ordering of requests and data. When a device
makes a request, the bus might indefinitely lock the write access to a
shared output link until the initiating device finishes its
transaction. If the initiating device does not finish the transaction
quickly enough, this can prevent other devices from using the bus,
causing a denial of service.

A "manager module" is a hardware component that initiates transactions
on the interconnect, such as a processor, DMA engine, or hardware
accelerator.

MODES OF INTRODUCTION:

Phase: Architecture and Design

Note: This occurs if the on-chip communication interconnect is based
on a multi-channel on-chip communication standard assuming cooperative
behavior among the manager modules AND an unsafe switching methodology
(e.g., cut-through) is in use.

Some switching methodologies may be susceptible to this weakness in
modern on-chip multi-channel communication standards, such as the
cut-through switching policy, a switching methodology for high
performance commonly implemented at the interconnect level. In
cut-through, a request is propagated independently on the receipt at
the interconnect level of the corresponding data. If the manager module
issuing a write request delays the provisioning of the corresponding
data, the other manager modules experience delays in accessing the
bus. Such delays are capable of generating denial of service.

COMMON CONSEQUENCES:

Scope: Availability

Impact: Memory-access delays; Denial-of-Service; I/O access delays, Deadline miss

Likelihood: High

Note: The attacker can leverage this weakness to generate unbounded
delays and denial of service (DoS) in the access of shared resources. The
system interconnect might be left in an inconsistent state, requiring
a partial or full reset of the network, according to the
implementation.

The scenario may play out as follows. The interconnect receives a
write request from a controller initiator (e.g., sending the header to
the interconnect for writing N words of data, with N ranging from 1 to
the maximum burst length allowed). The interconnect then speculatively
propagates the request to the target peripheral through the shared bus
before the corresponding data are received at the interconnect. Here,
the word "speculatively" refers to the fact that the interconnect
propagates the request, assuming that the controller will at some point
provide the data, thus releasing the use of the bus.  This
speculatively reserves the bus to the manager transaction issuer,
which is left free to delay its data provisioning phase.  This
reserves the whole bus path between the initiator and the target
peripheral until all of the words associated with the request are
provided by the controller.

If the interconnect assumes a cooperative behavior from the
controller, it is implicitly trusting that the controller will
complete the transaction and release the bus for use from the other
controllers. A malicious, faulty, or misbehaving manager module can
generate a denial-of-service condition in preventing access to the
write data link from all of the other managers in the system, and
unboundedly inhibit the write access to one or multiple peripherals in
the system (i.e., memories, I/Os, etc.).

DEMONSTRATIVE EXAMPLES:


INTRO TEXT:

In a system-on-chip, multiple hardware components may communicate with
shared resources through an interconnect. A manager initiates
transactions, while a target is a shared resource such as memory or a
peripheral. A shared write path is the portion of the interconnect
used by multiple managers to send write data to the same target.

To reduce buffering requirements and propagation latency, an
interconnect may use cut-through switching. In protocols where the
write request and corresponding write data are transferred
independently, the interconnect can forward the request before all of
the associated write data have arrived.

EXPLANATORY TEXT:

[SEE IMAGE ES2208-9fb81a1a-cut-through.png]
https://github.com/CWE-CAPEC/CWE-Content-Development-Repository/blob/main/submissions/ES2208-9fb81a1a-cut-through.png

(a) Manager A issues a multi-word write request.

(b) The interconnect forwards the request to the shared target before
receiving all corresponding write data. The shared write path is
reserved for Manager A until its data transfer completes.

(c) Manager A delays or stops sending the remaining data. The
transaction remains incomplete, and the shared write path remains
reserved.

(d) Manager B attempts to use the same shared path but cannot proceed
until Manager A completes the data transfer or a recovery mechanism
safely releases the path.

In these diagrams, "reserved" refers to the shared write path serving
the target, rather than every operation or route to that target.

EXPLANATORY TEXT:

The interconnect reserves the shared write path before the data
required to complete the transaction are available. In the problematic
design shown here, other managers cannot use that shared write path
until the corresponding data transfer completes. Thus, the
interconnect depends on Manager A to continue making forward
progress. If Manager A stalls, the stall propagates into the shared
portion of the interconnect and prevents competing transactions from
using that shared write path.

A faulty or malicious manager can delay or stop providing the
remaining write data. If the interconnect does not enforce bounded
progress or provide a recovery mechanism, the manager can hold the
shared write path indefinitely and cause a denial of service for
competing write transactions that require the same shared write path.


GOOD CODE:

LANGUAGE: Other


EXPLANATORY TEXT:

The interconnect should avoid reserving the shared write path until
the data needed to complete the forwarded transaction are
available.

One approach is store-and-forward switching the interconnect buffers
the request and all corresponding write data before forwarding the
request, preventing a manager's input-side stall from propagating into
the shared write path. If Manager A delays or stops sending data, its
incomplete transaction remains in the input buffer, and the shared
write path remains available to transactions from other managers.

Figure 2 - Store-and-Forward Switching

[SEE IMAGE ES2208-9fb81a1a-store-and-forward-1.png]
https://github.com/CWE-CAPEC/CWE-Content-Development-Repository/blob/main/submissions/ES2208-9fb81a1a-store-and-forward-1.png

(a) Manager A issues a multi-word write request.

(b) The interconnect buffers the request and waits for all
corresponding write data. The request has not been forwarded, and the
shared write path is not yet reserved for Manager A.

(c) After all data have been received and buffered, the interconnect
forwards the request to the shared target.

(d) The interconnect forwards the buffered data without waiting for
additional data from Manager A. Completion of the data transfer
releases the shared write path. The target completes the write and
returns a response through the interconnect to Manager A.

Store-and-forward requires storage for an entire transaction,
increasing buffer capacity and hardware area. It also adds buffering
latency because forwarding begins only after all corresponding data
have arrived. [REF-XXX]


GOOD CODE:

LANGUAGE: Other

Cut-and-forward is a second preventive approach. It divides a
transaction into smaller transactions and forwards each only after all
data for that chunk have been buffered. Like store-and-forward, it
prevents a manager's data-provisioning stall from reserving the shared
write path. [REF-XXX]

Cut-and-forward applies the same principle at a smaller chunk
granularity.  In Figure 3, a four-word write is divided into two
chunks of two words each. The interconnect creates the shorter
transactions and combines their responses, so Manager A continues to
issue and receive a response for the original transaction. [REF-XXX]

Figure 3 - Cut-and-Forward Switching

[SEE IMAGE ES2208-9fb81a1a-cut-and-forward-2.png]
https://github.com/CWE-CAPEC/CWE-Content-Development-Repository/blob/main/submissions/ES2208-9fb81a1a-cut-and-forward-2.png


(a) Manager A issues a four-word write request.

(b) The interconnect buffers the request and begins receiving the
corresponding write data. The request has not been forwarded, so the
shared write path is not yet reserved for this transaction.

(c) After the first two words have been buffered, the interconnect
creates a two-word write request and forwards it with the complete
first chunk to the shared target. While forwarding this chunk, the
interconnect can receive and buffer the next two words.

(d) After the remaining two words have been buffered, the interconnect
creates and forwards a second two-word write transaction with the
complete second chunk.

(e) The shared target completes the two shorter transactions and
returns a separate response for each one.

(f) The interconnect waits for both responses, combines them into the
single response expected for the original transaction, and returns
that response to Manager A.

The shared write path is reserved only when a complete chunk is
ready. If Manager A delays data for a later chunk, the incomplete
chunk remains in the input buffer; the path is not held while waiting
for those data and remains available to other managers. Smaller chunks
reduce buffering requirements and forwarding delay but increase
target-side transaction and response overhead. Larger chunks reduce
that overhead but require more buffering and increase the delay before
forwarding begins. [REF-XXX]

GOOD CODE:

Language: Other

A watchdog with protocol-aware recovery is a third, separate
mitigation approach. It limits the duration of a stall by restoring
the shared path to a usable state. It does not prevent the stall from
entering the shared path: other managers may remain blocked until
detection and recovery complete. Detection alone does not release the
path. [REF-YYY]

EXPLANATORY TEXT:

The behavior illustrated here has been demonstrated in AXI-based
interconnects. The weakness is not inherently specific to AXI and can
arise in other interconnect protocols with equivalent request/data
separation, ordering, resource-commitment, and progress
properties. The diagrams omit signal-level details to focus on the
shared write path and transaction sequence. [REF-XXX][REF-YYY]
