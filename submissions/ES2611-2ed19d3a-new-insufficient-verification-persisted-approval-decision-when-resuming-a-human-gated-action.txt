NAME: Insufficient Verification of Persisted Approval Decision When Resuming a Human-Gated Action

DESCRIPTION:

The product suspends execution at a human approval gate and persists the
pending decision to a state store such as a checkpoint, session, task
record, or execution history. On resume, the product reads a persisted
approval value and treats it as authorization to execute the gated action.
That value can be an approved flag, a completed human-task status, an
approval review record, or an approval event. The product does not verify
that the value originated from the authorized approval path, and it does
not verify that the value is bound to the action being executed.
 
A persisted approval value records a decision but does not prove its
origin. Any principal with write access to the state store can create the
value the resume path accepts, without authenticating as the approver.
 
Write access to workflow state is a narrower privilege than approval
authority. Migration jobs, recovery services, sidecars, backup agents, and
scoped database roles write workflow state as part of normal operation, but
hold neither approval rights nor the credentials of the gated action. When
such a principal sets the approval value, the product executes the action
with its own service identity. This is a confused-deputy condition. The
approval control is bypassed, and a privileged operation such as a payment,
deployment, access grant, or tool invocation executes on behalf of a
principal that cannot perform it directly.
 
The audit trail is also compromised. Execution records attribute the
decision to a named approver who never acted, which produces false evidence
of human oversight and breaks accountability and non-repudiation.
 
The weakness arises at the trust boundary between a framework and the
application deployed on it. The framework exposes the gate as a security
control but assigns state integrity to the application. The application
relies on the gate to enforce approval. Neither component verifies approval
provenance.

Variants:
 
1. Argument rebinding. The approval is not bound to the action's arguments.
The arguments are modified after approval, and the original approval
authorizes the modified action.
2. Replay. The approval is not bound to a run, target, validity window, or
single use. It is reused outside its intended scope.
3. Gate suppression. Persisted state, such as a risk classification,
approver policy, or trusted-tool list, determines whether the gate
executes. Modifying it skips the gate, and no approval record is created.
4. Approval laundering. A downstream system accepts an unverified upstream
approval as authorization, which grants it authority it never carried.
